# 悬浮窗分辨率与缩放切换定位修复

## 原因和修改范围

基线提交：`85ec2f8d20b001c3008410ad4ff24a1222b0c727`，开发分支 `codex/2.0`。

默认／灵动岛原先只保存绝对坐标，分辨率缩小时将越界坐标裁剪到工作区域内，并把裁剪结果写回配置。复现中，保存的 x=2100 在 2560×1440 → 1920×1080 → 1280×960 → 2560×1440 后变为 880，无法恢复。

竖排窗口保存的是物理坐标，创建时却传给逻辑坐标接口；同时将所有 Moved 事件当成用户拖动，系统自动调整也会覆盖保存值。

本次改动：

- `overlay_position.rs` 保存定位基准，按可放置区域的相对位置计算目标物理坐标。
- `overlay_display.rs` 优先按已保存的显示器设备名查找当前工作区域，显示器不在时回退到最近显示器，不覆盖原基准。
- `overlay_panel.rs` 只在手动拖动结束时替换坐标和基准；兼容没有基准的旧配置，自动裁剪不再覆盖坐标。
- `vertical_overlay_position.rs` 在窗口所属线程使用系统子类回调区分原生拖动与自动移动。拖动结束时原子记录坐标和基准，利用已有后台循环持久化；已有置顶循环同时处理显示区域变化。
- `lib.rs` 按物理像素恢复竖排窗口，保留设置保存时的两个原生定位基准，重置时只清除对应基准。退出仍使用内存中的坐标，不查询已关闭的 WebView。
- `VerticalOverlayPage.tsx` 不再监听所有 Moved 事件写配置，也不再从迟到的 JS 回调读取最终坐标；窗口实际内容加载后才提供布局尺寸。

采集、PresentMon、报告和更新安装链路未修改，发行版本号仍为 `2.0.0`。

原生窗口测试只创建不可见的独立 HWND，调用真实 comctl32 子类回调：程序移动不提交坐标，手动移动提交坐标和显示器基准，拖动期间自动适配不抢位置，自动适配后仍保留手动基准，销毁不重置坐标。未启动游戏、未修改显示模式、未操作用户正在运行的 FrameScope。

## 验证边界和兼容性

- 未打包、未发布、未覆盖本机安装版。实际游戏中改变 Windows 显示模式及 4:3 拉伸／黑边的表现仍需新候选运行验收，不能用单元测试替代。
- 这里适配的是 Windows 提供的显示器工作区域；游戏只改变内部渲染分辨率、未改变 Windows 显示区域时，不推测游戏内部视口。
- 旧配置缺少定位时的分辨率。旧坐标仍可见时采用当前显示区域建立基准；越界时仅临时限制实际窗口，不改写旧坐标。旧版本已经覆盖丢失的位置无法凭现有配置还原，可重新拖动一次建立新基准。
- 回退使用本次提交的 revert；新增 JSON 字段由旧版忽略，既有坐标字段保留。用户配置、报告、签名密钥不属于提交内容。
