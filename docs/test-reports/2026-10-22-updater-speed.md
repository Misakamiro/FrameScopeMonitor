## 定位证据

当前公开发行列表以 beta.2 为最新可用测试输入。本机 beta.3 是本地候选；测速 beta.2 不代表允许向用户提供降级更新。

首轮对同一个 88,300,032 字节的标准安装包并行请求前 4 MiB，使用 Windows curl，连接期限 4 秒、总期限 16 秒；单次样本限制 4 MiB，服务器忽略 Range 时另设大小上限。测量结果：

| 路径 | 首轮结果 | 说明 |
| --- | --- | --- |
| GitHub 原站，不使用环境代理 | HTTP 302 后，连接 release-assets.githubusercontent.com 超时，0 字节 | GitHub 页面可连接不能证明安装包 CDN 可连接 |
| GitHub 原站，显式使用本机 127.0.0.1:7897 代理 | 4 MiB / 1.997 秒，约 2.10 MB/s | 当前代理确实可以传输安装包 |
| gh-proxy.org，不使用环境代理 | 4 MiB / 2.829 秒，约 1.48 MB/s | 当前加速站存在可用线路 |
| gh-proxy.org，经本机代理 | 4 MiB / 2.308 秒，约 1.82 MB/s | 加速站和本机代理可以同时使用 |

这是当前时段、当前机器的观测。网络会变化，后续 Rust 原站探测也曾收到数据，不能据此宣称原站始终不可达，也不能把不同样本大小的速度差直接解释为软件提升倍数。

代码确认两处应用层问题：

1. 原来下载与元数据共用线路偏好。发行 API/清单成功会让该线路被优先用于完整安装包，而安装包在跳转后的 CDN 路径可能不同。
2. 下载只检查连接、无数据读取和总期限。只要持续收到少量数据，低速流不会触发线路切换；可一直拖到 30 分钟总期限。

先写测试并运行旧实现：安装包线路探测数量为 0（期望 2）；持续低速测试直到人为取消才退出（期望低速回退）。两项均按预期失败，见 `red.log`。

## 修复

- 在签名清单校验通过、确认版本身份未改变后，再探测实际安装包 URL。
- 开启加速时，并行读取 GitHub 原站和既有 gh-proxy.org 两条路径的最多 256 KiB 数据；每条最多 6 秒。按包含连接/首字节等待的样本速度排序，不根据小型清单的成功推断整包速度。
- 服务器忽略 Range 时只读取前缀并丢弃响应，不为了测速下载第二份完整安装包。不支持/未完成探测的线路仍保留为备用，不因探测不兼容直接阻止下载。
- 首选线路每 8 秒检查一次实际收到的字节；不足 64 KiB/s 时终止该连接并尝试另一条。最后一条可用线路允许低速继续，避免低带宽用户被反复中断。原有 30 分钟总期限保持不变。
- 换线重新下载整个文件并重新校验大小和 SHA256，进度重置。清单与签名已独立校验，不要求安装包和清单必须来自同一条网络线路。
- 取消会同时丢弃两个探测/当前下载连接，没有后台脱离的下载任务。关闭加速时不探测、不访问第三方，只使用原站。
- UI 说明同步更新，无新增镜像、配置项、持久化格式或依赖。

改动文件：

- `src/updater/src/lib.rs`：分离清单校验和安装包线路选择，保留按序回退及最终验证。
- `src/updater/src/download.rs`：受限并行样本、速度排序、持续低速检测、取消连接。
- `desktop-preview/src/preview/settings/UpdateSettings.tsx`：新下载策略说明。
- `src/updater/src/download_tests.rs`：真实本地 HTTP 服务器回归，含慢流、断连和篡改。
- `src/updater/examples/download_diagnostic.rs`：仅下载到明确隔离缓存、不安装的实网诊断程序。
